## GEN-002: Failed writes are never rolled back on the shared request connection

**Setup.**
- `app.py:26-29` opens a single connection with `check_same_thread=False` and stores it on `app.state.db`.
- `deps.get_db` hands that same object to every request.
- All endpoints are sync `def`, so FastAPI runs them concurrently on its threadpool.
- Python's `sqlite3` (default `isolation_level=""`) issues an implicit `BEGIN` before the first INSERT, UPDATE or DELETE.
- `grep -rn rollback backend/src` finds nothing.

**Evidence, run against the real modules on a scratch database:**
- `collection_service.add_images(c, id, ["f"*64, "a"*64])` raises `IntegrityError: FOREIGN KEY constraint failed`, and afterwards `c.in_transaction` is True. `INSERT OR IGNORE` does not suppress FK violations, which contradicts the docstring at collection_service.py:139-140.
- `delete_collection` after a vote behaves the same way (GEN-003).
- Adding images to a `source_preset` collection raises `IntegrityError: source_preset collections do not store image rows` (a trigger from migration 005). `api/collections.py:99-109` does not check the collection type first.
- Minimal repro: a failed FK insert leaves a connection inside a transaction. A second connection with `timeout=0.2` then gets `database is locked` on INSERT.

**Paths that leave the transaction open:**
- `api/tags.py:52-55`: a duplicate tag returns 409.
- `api/sources.py:61-68`: a duplicate source returns 409.
- `tag_service.update_tag` (lines 62-66): renaming a tag to an existing name raises an uncaught IntegrityError, so the response is 500.
- `api/tags.py:87-95`: tagging a well-formed but unknown hash fails the FK check, so the response is 500.
- `collection_service.add_images` and `delete_collection`, as above.
- `api/elo.py:65-72`: a `record_vote` failure is turned into a 400, but nothing rolls back.

**Consequences:**
1. The request connection keeps its RESERVED lock until some unrelated request calls `commit()`. Until then, every write on the scan worker's own connection (sources.py:142) waits 5 s and fails with `database is locked`, and each of those files is counted as a scan error.
2. The connection is shared across threads, so one request's `commit()` can commit another request's half-finished multi-statement work. For example, `delete_source` (sources.py:85-116) issues six statements before it commits. It works the other way too: an error in one request leaves a transaction open, and another request then commits it.

**Suggested fix:** Use `with conn:` in each write service, which commits on success and rolls back on exception. Better still, open a connection per request: make `get_db` a dependency that uses `yield`, and in `finally` roll back if `conn.in_transaction`. That also stops transactions from different threads interleaving.

**Done when:** A test calls each failing write endpoint and asserts that `app.state.db.in_transaction` is False afterwards. With per-request connections, the test can instead assert that a second connection can write immediately.
